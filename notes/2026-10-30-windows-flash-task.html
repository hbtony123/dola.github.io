一闪而过的终端窗口
给 Windows 计划任务做一次「窗口审计」

屏幕每隔一阵闪一下，像有个终端窗口一闪而过。查显卡之前， 先查一个更平常的东西：计划任务里有没有人直接拉起可见的 PowerShell。

这类闪窗有一个很容易被忽略的特征：规律。它不随画面内容出现， 不随游戏或视频负载变化，而是隔一段时间来一次，每次只有零点几秒。 这种节奏更像是某个定时器到了点，而不是显示链路在抖。 顺着「谁在定时启动东西」去查，方向就窄了一半。

先排除上次修过的那个

这台机器之前修过一次同类问题：同步任务的包装脚本用 python.exe 启动， 控制台窗口被 Windows Terminal 接管，于是每隔一分钟闪一下。 当时的修法是改走 pythonw.exe，并让计划任务在非交互会话里跑。 复测时在任务启动的瞬间抓它的进程链——pythonw → PowerShell → conhost， 逐个取三个进程的窗口句柄，结果全部是 0，说明整条链路没有任何可见窗口。 旧案不是复发。

把最近新建的任务翻出来

排查真正有效的入口不是「计划任务库里有什么」，而是「最近多了什么」。 按创建时间排序，一个新出现的任务远比一个运行了几年的任务可疑： 

Get-ScheduledTask |
  Where-Object { $_.TaskPath -notlike '\Microsoft\*' } |
  Sort-Object -Property @{ e = { ($_ | Get-ScheduledTaskInfo).LastRunTime } } |
  Select-Object TaskName, TaskPath, State

这次很快就看到一个当天凌晨创建的条目：ClaudeHealthCheck， 每 30 分钟运行一次，动作为直接启动 powershell.exe 执行 C:\bin\health-check.ps1。而 C:\bin 这个目录并不存在， 脚本自然也不存在。任务每次运行都以失败告终（错误码 0xFFFD0000）， 但 PowerShell 进程在被拉起的那一瞬间照样产生了一个可见的控制台窗口—— 失败的是脚本，不是窗口。

判断顺序： 先看闪窗的节奏是否规律，再看最近新建的计划任务，最后才怀疑显示硬件。 计划任务的失败记录不会阻止窗口出现——它只说明任务没干成事。

处理：禁用比删除稳妥

在管理员会话里禁用任务，配置原样保留： 

schtasks /Change /TN "ClaudeHealthCheck" /DISABLE
schtasks /Query /TN "ClaudeHealthCheck" /V /FO LIST

复查输出里 Status 为 Disabled、Next Run Time 为 N/A，任务就算停住了。保留配置而不是删除，是因为这类「健康检查」 通常出自某次自动化实验，脚本补回去之后随时可以重新启用； 删除反而让人再也不敢确认当初是谁建的。

收尾时再把所有「启用、且动作里带 powershell/cmd/python」 的任务过一遍，确认没有第二个会亮窗口的条目，这次排查才算闭环。

两个容易被忽略的细节

第一个细节是权限。用普通账户远程查询这个任务时，schtasks 和 Get-ScheduledTask 都只回一句「拒绝访问」——看任务是否真的被禁用， 必须用管理员会话复看，否则很容易把「查不到」当成「已经没了」。

第二个细节是习惯。以后给这台机器加定时任务，动作一律走 pythonw.exe、-WindowStyle Hidden 或干脆做成服务； 脚本路径写死在任务里之前，先确认文件真的存在。 闪窗的根因往往不是任务本身设计错了，而是它「以为」自己很安静。

复盘下来，这次问题的全部成本只有一次任务列表排序和一次禁用操作。 真正拖时间的，是看到屏幕闪就先想到显卡的那个直觉—— 而终端窗口的轮廓，本身就是操作系统发给我们的第一条线索。 回到笔记
