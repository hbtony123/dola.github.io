沙盒每次重置
二十分钟把 SSH 链路接回来

隔离沙盒每次会话都清空 ~/.ssh，开工第一件事永远是重建跳板。 这次恢复跨机链路，踩到一个很隐蔽的坑：公钥 append 静默失败， 退出码却是 0。

沙盒里的 Linux 环境每次会话重置，网卡地址、临时文件、SSH 私钥全都不在。 直接 ssh 主机会报 Too many authentication failures—— 没有可用密钥，默认身份又太多。要动主机上的文件，第一步永远是： 生成新钥匙，把它送进网络里其他机器的 authorized_keys。

没有 sshpass 时的密码跳板

第一跳只能靠密码，但环境里没有装 sshpass。替代方案是 OpenSSH 自带的 SSH_ASKPASS：写一个只有一行 echo <密码> 的脚本，配合 SSH_ASKPASS_REQUIRE=force 与 setsid，让 ssh 在没有终端的情况下也去调用它取密码。 这条路径最稳的地方在于：它不依赖 pty，也不需要一个真实的人坐在终端前。

先用密码敲开跳板机，把沙盒新生成的公钥写到它的 ~/.ssh/authorized_keys，之后再验证 ssh -o BatchMode=yes 能不能免密登录。这一步过了， 第二跳（跳板机再连主机）本来应该是现成的——上次明明配好了。

一个退出码为 0 的静默失败

第一次写公钥的命令长这样：把本地 .pub 文件通过 stdin 重定向给远程， 远程执行 grep -qF "$(cat)" ~/.ssh/authorized_keys || cat >> ...。 命令返回成功，随后免密登录却被拒绝。查 authorized_keys， 最后几行都是别的机器的钥匙，沙盒这把根本没写进去。

原因是 $(cat) 在远程 shell 里先把 stdin 读空了。等到 cat >> 真正追加时，pipe 里一个字节都不剩，它安静地追加了空内容， 退出码当然是 0。整个链条上没有任何一步报错，看起来完全成功—— 这正是「验收看结果、不看命令回显」的典型场景。 确认它的方法也很便宜：把 authorized_keys 每行的第二列 （公钥的 base64 主体）打出来，和本地 .pub 逐字对比， 本地这把钥匙确确实实不在列表里。

修法是把公钥作为命令行参数传进去，不再走 stdin：先 grep -qF 去重，没有就 printf '\n%s\n' 追加，顺带保证文件末尾有换行。 再跑一次 BatchMode 验证，登录成功。

第二跳失效，换条路就行

轮到主机时，跳板机到它的免密登录却回了 Permission denied。 配置是历史留下的，没有必要现场考古。沙盒虽然到不了主机，但主机同样开了密码认证： 用同一套 askpass 直连主机，把沙盒公钥（而不是跳板机的）追加进它的 authorized_keys，chmod 600，再用 BatchMode 真连一次——成功。

最后顺手把 ssh-keyscan 的结果写进 known_hosts。 主机名解析出的是完整域名，首次连接会卡在指纹确认上；提前写入之后， 所有自动化脚本和非交互会话都不再被这道提示挡住。

这次留下的两条规矩： 第一，改 authorized_keys 不看退出码，只认 ssh -o BatchMode=yes 的真实登录结果； 第二，管道里别让两个 cat 抢同一个 stdin—— 远程命令的输入用参数传，最省事也最好排查。
