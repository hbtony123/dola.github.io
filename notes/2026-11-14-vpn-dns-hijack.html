每个新网页都慢 2 秒：一次 VPN 接管 DNS 的排查记录

网页能打开，但每个没缓存过的域名都要等 2 秒。ping 正常、带宽正常，问题藏在系统的 DNS 解析顺序里。

现象很怪：同一个网站第二次打开瞬间就出来，换一个新的域名就卡两秒。测带宽、测 ping 全部正常， 只有"第一次"的那一下卡住。这个特征本身就说明问题：两秒是一个整齐的等待值，不是网速慢，是某个环节在等超时。

一、分层测：链路、解析、代理分开看

先测网关（0.6ms）、再测公网 IP（0.5ms），都正常，说明链路没问题。接着逐个 DNS 服务器对比： 本机 192.168.0.103 上的解析服务 30ms 就回，10.42.100.1 的隧道 DNS 却要 2 秒多。 但直接 dig 单问一个服务器时速度并不总是慢，按缓存状态飘忽。

真正露馅的是对比记录类型：同一个服务器，查 A 记录（IPv4）要 2078ms，查 AAAA 记录（IPv6）只要 27ms。 两秒跟网络毫无关系，是这个 DNS 服务自己内部在等什么。

二、找到优先级最高的那个解析器

scutil --dns 里，排在第一位的解析器不是手动设置的公共 DNS，而是一块隧道网卡 utun7 上的 10.42.100.1，标记 Supplemental、order 104400——这个数值比普通网卡的解析器小，系统会优先问它。 也就是说，在路由器/网卡里设置 223.5.5.5 根本轮不到用。

查进程时间线：这个 VPN 工具是前一天晚上装的，当天上午才自动启动；它启动之后，默认路由也被改指向隧道网卡。 对一下时间，"今天网站变慢"和"VPN 今天开始跑"完全重合。

把隧道进程停掉之后，默认路由立刻回到物理网卡（gateway 192.168.0.1），域名解析从 2005ms 掉到 15~20ms， 新域名、老域名都正常。到此把原因钉死了：不是运营商、不是路由器、不是 DNS 服务本身坏了， 是一个 VPN 把优先级更高的解析器挂到了系统上。

三、为什么手动设置的 DNS 会被"顶掉"

macOS 的 DNS 不是"你填什么就用什么"。VPN 类工具通过网络扩展（Network Extension）获得权限后， 可以向系统注册自己的解析器，并带上 supplemental 标记和小 order 值，从而排在用户配置之前。 设置面板里的 DNS 看起来还在，实际查询根本不走它。

这类工具通常还会同时接管默认路由和系统代理（HTTP/SOCKS），形成一个完整的流量出口。 好处是干净，坏处是——它自己的 DNS 出问题时，整个系统的解析一起遭殃，而且用户从设置界面完全看不出来。

四、留下的教训

"网慢"先分层：链路（ping）→ 解析（dig 逐服务器、A/AAAA 分开计时）→ 代理（逐工具确认谁在接管路由）。 两秒整的延迟几乎总是"超时等待"，不是带宽问题。

装了 VPN、加速器、安全软件，就默认它们可能改了 DNS 和路由。出事先看 scutil --dns 里 resolver 的顺序和 route -n get default 的网卡，比在设置页里翻来翻去有效得多。
