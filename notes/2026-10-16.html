被 127.0.0.1
骗了一整天

我们用一天时间，把 dola.cn 从一个准备废弃的旧页面换成现在这个站，顺手给域名接上了邮箱。 过程里每一个环节都「看起来成功了」——这是今天最贵的教训。

先说清楚为什么值得写下来：这一天里，我们至少五次收到「成功」的信号——认证成功、命令没报错、页面能打开、 配置显示生效——而它们全都不是真的成功。真正花掉时间的地方，不是技术本身，而是分辨真假。

01 · 早上：推倒重来

起因很简单：dola.cn 上那份旧页面早就没人维护，字里行间都是「准备废弃」的气息。于是决定重做—— 不做通用模板，只做一页能长期活下去的东西：几个页面、一份样式表、没有框架、没有构建步骤， 任何人打开源码都能看懂它怎么工作。

我们对发布只提了一条要求：一条命令搞定。而且这条命令必须自己验证结果， 而不是自己宣布成功。这句话说完不到两小时，就被现实打了脸——而且打的正是这句话。

02 · 中午：一个骗过我的 127.0.0.1

仓库在 GitHub Pages 上。按常理，克隆、提交、推送，是三分钟的事。第一次 git clone 就失败了。 查下去发现：这台机器上 github.com 被解析到了 127.0.0.1——本地有个代理在接客。

更妙的是，它接得很有礼貌。用 SSH 连上去，它回一句「You've successfully authenticated」：认证通过。

问题是，我当时手里那把密钥是刚生成的、从没上传到任何地方的。它不可能通过任何真实的验证。

知识点｜怎么识破「假的成功」
拿一把注定不该成功的钥匙去试。如果它也能开门，那这扇门就是假的。 我们当时立刻用一把随手生成的密钥复现了同样的「成功」，于是确认这个入口不可信。

真入口后来找到了：GitHub 的 SSH-over-443，也就是 ssh.github.com:443。 它解析到真实 IP，用机器上早就注册过的那把密钥验证——仍然是「成功」，但这次我们先用 API 交叉核对了提交哈希，确认它确实连到了真仓库，才敢继续往下走。

03 · 下午：0 字节的包

真通道找到了，克隆还是不动。一看本地仓库的 objects/pack：临时文件停在 0 字节，从头到尾没长过一个字节。可 ls-remote 却能秒回—— 说明握手没问题，是传数据这一步断了。

换成浅克隆 --depth 1：5 秒，6.2 MB，完事。 仓库里那 3 MB 的音频、几百个历史对象，我们其实一个都不需要。

知识点｜「命令报错」和「事情没成」是两件事
判断发布成功，永远不要只看命令的退出码，要看结果本身。 我们后来给自己的做法是：抓取线上首页，和本地文件逐字比对。

顺带交代：我们自己的发布脚本一开始也犯了这个错。它那句「已上线」判断，检查的是新旧版本里都存在的文字—— 等于没验证，只是把「没报错」当成了「成功」。改成逐字比对之后，它才真正有资格说话。

04 · 傍晚：顶点之争

站点上线之后，轮到邮箱。邮箱要能收信，得在 DNS 里放 MX 记录；而 dola.cn 的顶点 （也就是 @ 本身）当时挂着一条 CNAME。

知识点｜CNAME 是独占记录
同一个名字下，CNAME 不能和 A / MX / TXT 共存——这是 DNS 规范，不是某个服务商的偏好。 所以顶点要收信，就得先把 CNAME 换成 A 记录。GitHub Pages 官方对顶点域名的要求，本来也是 4 条 A 记录。

换完，邮箱记录一条条加进去：MX 三条、SPF 一条。这时又冒出第二个坑—— mail._domainkey.dola.cn（DKIM 该待的地方）查出来指向了 GitHub Pages。 原因是我们之前配了一条通配符 * 的 CNAME：通配符会接管所有没有显式记录的名字， 包括 mail._domainkey 和 _dmarc，于是 DKIM 永远配不上。

删掉通配符，这两个名字空了出来，MX 和 SPF 原样还在，站点毫发无伤。

05 · 晚上：邮箱在收信，却不让我进门

MX 就位之后，我们先做了一次硬验证：直连对方的收信服务器，用 SMTP 协议问一句 「这个收件人存在吗」。结果是：

hello@dola.cn → 250 Rcpt Ok； 随手编一个不存在的地址 → 554 doesn't exist。 一个真、一个假，这才叫验证通过。

（第一次这样测的时候，整台服务器把我们拒了——因为我们用的发件人域名没过对方 SPF 校验。 换成空发件人 MAIL FROM:<> 就绕过了这一层。）

收信没问题。但当我们要以 hello@dola.cn 的身份登录收发时，服务器一律回： 认证失败。于是一轮现在回想起来有点好笑的排查开始了：换了几种登录名写法、 换了两套认证方式、把重置密码的思路都铺好了……所有线索都指向「密码不对」。

06 · 深夜：一条被忽略的黑名单

最后是翻后台翻出来的。在「访问策略」那一页，安安静静躺着一条谁都没注意的策略： 名称「禁止使用三方客户端」，类型「黑名单策略」，生效对象「所有用户」， 适用客户端「三方客户端」，状态「开启」。

它开着，就意味着任何第三方邮件客户端都进不来。而服务器给出的报错是「认证失败」—— 把人稳稳地引向密码那条岔路。

关掉它，再登一次：

[mail] login OK
[mail] inbox: 3 messages
[mail] self-test message sent, waiting 25s for it to arrive...
[mail] inbox now: 4 messages (was 3)

密码从头到尾都是对的。

知识点｜认证失败 ≠ 密码错
认证失败只说明「这个组合没通过」。原因可能是密码、可能是策略、可能是 IP 限制。 建议的排查顺序是：先看服务端的策略开关，再怀疑凭据——改密码是成本最高、也最容易白改的那一步。

07 · 今天最值钱的一课

到深夜，该到位的都到位了：站点一条命令发布、域名解析干净、邮箱能收能发、凭据加密存在本机。 但真正值得记下来的是另一件事。

一天里的「假成功」与真正的证据
看起来成功了真正的证据
SSH 提示「认证成功」用一把不该成功的密钥试一次
克隆命令跑完了数据包真的从 0 字节长起来
发布脚本说「已上线」线上首页与本地文件逐字一致
邮箱记录「添加成功」向权威服务器查 MX / SPF 真的在
收件人地址可用同域下编一个不存在的地址会怎样
后台显示一切正常报文里没有一条「禁止三方客户端」

「看起来成功了」是今天最贵的假象。 要拆穿它，办法只有一个：找一个能区分真假的证据。能反证、能对照、能自己复现的，才算数。
