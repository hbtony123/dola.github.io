每天 08:25，让 AI 写一篇观察
并自己发布：三道闸门

GitHub 热点观察每天一篇。写稿的是模型，但数字必须来自当天的快照。 为了让“每天一篇”不变成“每天一篇幻觉”，这条流水线设了三道闸门， 每道闸门失败时都只有一个出口：不发布，保留上一期。

第一道：素材只有一天的事实

08:05，采集任务先把 GitHub 公开 API 的快照落盘：近七天新建、 Star 100 以上的仓库，近七天有推送、Star 1,000 以上的仓库，各自拉一份。 08:25，写稿任务只读这一份快照，先生成一个事实文件——增速前十五的仓库、 主题合计、最近五期的标题，仅此而已。

提示词里写死了三条：只许使用事实文件里的数字；简介为空的仓库不许猜用途； 正文最多引用六个数字，因为证据表已经负责数字。 写手拿不到别的“记忆”，也就编不出当天的 Star 数。

第二道：写完必须过数值校验

稿子落到临时目录后先过校验：日期和期号对不对、小节三到五个、 正文七百到一千八百字、证据表四到十行。每一行的仓库必须出现在当天的事实文件里， 增量数字必须一字不差，链接必须与快照一致，来源只允许仓库链接。

任何一条不符，这一期直接作废：页面保留上一期，同时发一封邮件说明失败原因。 校验不是润色，它不判断文笔，只判断“这期说的数字是不是真的”。

试跑两次：第一次两分钟出稿，数字全对，但文风是一段一段报数； 给提示词补上“段落不要以净增数开头”之后，第二次两分半钟出稿， 一千二百多字、八行证据，读起来像一篇观察，而不是一份报表。

第三道：发布只允许动栏目自己的文件

通过校验后，发布脚本先生成一份复核声明，能改的只有五类文件： 栏目页、它的样式与脚本、每日索引、趋势数据快照。站点里其他任何本地改动 都会让发布中止——这一条是防“顺手把别的东西也发上去”。

发布照旧走既有流程：编辑检查跑两遍、推送后逐文件做线上哈希核验， 核验不过就保留旧版。原来 08:45 还有一个只发数据的旧任务， 这次给它加了一个判断：当天观察已经上线就安静退出， 避免一天两次发布、两封邮件。

失败是流程的一部分

没有新快照、增长窗口没成型、写手超时、校验不过、发布失败， 五种情况各有明确出口：前三种不发也不吵，后两种保留旧版并发信说明。 自动化最怕的不是失败，是失败了还装作成功—— 所以每期发布完都要等线上核验返回 200，才算结束。

给同类流程的一句话： 让模型写观点，让脚本管事实；两者之间放一道只认真假的闸门。 文风可以迭代，数字不能试错。
